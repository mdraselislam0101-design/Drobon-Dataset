## 4. Change made in this pass

**One fixture, four files.** `DPK-DAST-242` ("Private key material served in a response")
carried two positive fixtures whose bodies were well-formed base64 that decoded to a
DER-encoded DSA private-key structure. The bytes were not a usable key — the payload
degrades into a sequential character ramp (`1k2l3m4n5o6p7q8r9s0t1u2v…`) — but the shape was
realistic enough that a reader or an automated scanner cannot tell it apart from a real key
at a glance, and it is exactly the kind of artefact a secret-scanning gate is meant to
surface.

The bodies were replaced with an unambiguous `EXAMPLE` payload that still satisfies the
rule:

```
(PEM header) → two lines of the literal EXAMPLE repeated → (PEM footer)
```

| File | Change |
|---|---|
| `data/asset-cells/dast-20.json` | the two positive `observation.body` values (source of truth) |
| `packs/dast/v1/rules/DPK-DAST-242.json` | regenerated by `scripts/generate-assets.mjs` |
| `knowledge/patterns/DPK-PAT-1311.json` | regenerated |
| `data/eval-cases/EVAL-DAST-401.json` | authored artifact, updated by hand to keep the fixture consistent with the rule |

**Nothing was weakened.** The rule still requires a PEM header plus at least 20 base64-range
characters, and still has 2 positive and 2 negative tests (`validatePackFile` executes each
one). The negative cases — a bare footer and an ordinary HTML page — are untouched. The
evaluation case still reports `PASS` with 1 true positive.

**No detection was added or removed.** 0 candidates were proposed this pass, 0 IDs were
consumed, and the rule/pattern/record/remediation counts are unchanged. This pass was a
verification pass, not a coverage pass; the rejection ledger from the previous pump stands
unchanged.

## 5. Findings reported but deliberately not "fixed"

**The leak-guard regex is narrower than the rule it protects.** In
`scripts/generate-assets.mjs`, the strict pre-screen matches
`-----BEGIN (RSA |EC |OPENSSH )?PRIVATE KEY-----`. DSA, PGP, ENCRYPTED and other PEM labels
fall outside it, which is why the realistic DSA body above passed the generator's own leak
check on the way in. Broadening the pattern is a one-line change, but it would immediately
fail on the two DAST fixtures that legitimately need a PEM header, so a correct fix needs an
explicit, reviewed exception path — a design decision about a security guard, not a drive-by
edit. It is recorded here for the owner instead of being changed unilaterally.

After this pass, **no key material of any kind remains in the repository**: all nine
remaining PEM-header occurrences are header-only marker strings inside `packs/secrets/`
(the designated audit zone) or the evaluation case that mirrors one of them.

A second, smaller observation from the previous pass stands: `normalizeHeaders()` in
`scripts/validate-packs.mjs` passes non-string header values through unchanged, so a
malformed observation could throw at evaluation time. No current rule supplies such a value.
